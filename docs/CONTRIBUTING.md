# 협업 안내

스펙 주도 개발로 일한다. 만들기 전에 무엇을 만들지 문서로 정하고, 코드는 그 문서를 따른다. 문서는 두 종류다.

| 문서 | 하는 일 | 위치 |
|---|---|---|
| 영역 스펙 | 이 영역이 무엇이고 어떤 기능을 하는지. 지금 게임 동작의 기준 | [`specs/`](specs/README.md) |
| 작업 문서 | 작업 하나의 목표, 진행 상태, 승인, 할 일, 결과 | [`tasks/`](tasks/README.md) |

기획, 이야기, 아트, 기술 자료가 어디 있는지는 [`README.md`](README.md)를 본다. 코드 규칙은 루트 `AGENTS.md`에 있다. 이 문서의 절차는 에이전트가 따르고, 사람은 무엇을 만들지 말하고 승인만 한다.

## 진행 상황

진행 상태는 작업 문서에만 있다. 작업 문서 첫 줄의 `[제안]`, `[개발중]`, `[완료]`가 곧 승인 단계다. 지금 무엇이 진행 중인지 물으면 에이전트가 `dev`의 `docs/tasks/`에서 `[제안]`과 `[개발중]` 문서를 모아 답한다. 영역 스펙에는 진행 상태를 쓰지 않는다.

## 작업 순서

1. `specs/README.md`에서 바꾸려는 것의 영역 스펙을 찾아 읽는다. 고칠 기능의 ID로 "자세히"의 주의도 찾아 읽는다.
2. [`tasks/_TEMPLATE.md`](tasks/_TEMPLATE.md)로 작업 문서를 만들고 `[제안]`으로 둔다. "무엇을 만드나"와 "확인 방법"을 쉬운 말로 쓴다.
   - 새 기능이면 영역 스펙 맨 위 "다음 번호"를 ID로 쓰고, 다음 번호를 올린다.
   - 있는 기능을 바꾸면 그 기능의 ID를 그대로 쓴다.
3. 작업 문서와 번호 변경만 짧은 브랜치로 `dev`에 먼저 합친다. 번호를 먼저 차지하고, 다른 사람에게 진행 중임을 알린다.
4. 사용자가 승인하면 `[개발중]`으로 바꾸고, "어떻게 만드나"와 "할 일"을 쓴 뒤 기능 브랜치를 따서 구현한다. 할 일은 끝날 때마다 체크한다.
5. 다 만들고 "확인 방법"대로 확인하면, 기능을 영역 스펙의 "기능" 절에 반영하고 "코드 단서"를 채운다. 고칠 때 깨뜨리기 쉬운 점은 스펙의 "주의"에 남긴다. 작업 문서는 `[완료]`로 바꾸고 "결과"를 쓴다.

- 문서에 없는 동작을 코드에만 넣지 않는다. 구현 중 정해지지 않은 요구가 나오면 멈추고 작업 문서 수정을 제안한다.
- 모호하면 추측하지 않고 묻는다.
- 같은 기능에 새 영역 스펙을 만들지 않는다. 새 영역 스펙은 README에서 맞는 영역이 없을 때만 만든다. [`specs/_TEMPLATE.md`](specs/_TEMPLATE.md)를 `영역-이름.md`(소문자 영어, 번호 없음)로 복사하고, 다른 영역과 겹치지 않는 대문자 접두어로 README 표에 등록한다.
- 영역 스펙이 15편쯤 넘으면 `specs/gameplay/`, `specs/ui/`, `specs/tools/`, `specs/art/`처럼 분야별 하위 폴더로 나누고, README 표에 `gameplay/blink-maze.md`처럼 경로로 적는다.
- 문구 하나 고치는 정도의 작은 일은 작업 문서 없이 영역 스펙만 고쳐도 된다.

## 여러 브랜치에서 일할 때

- 번호는 영역마다 따로 매기므로 다른 영역끼리는 겹치지 않는다. 작업 문서도 작업마다 파일이 따로라 충돌하지 않는다.
- 같은 영역의 새 번호를 두 브랜치가 쓰면 영역 스펙의 "다음 번호" 줄에서 git 충돌이 나 겹침이 드러난다. 늦게 합치는 쪽이 자기 작업의 번호를 다음 번호로 바꾼다.
- 위 3번처럼 작업 문서를 먼저 `dev`에 합치면 이런 충돌이 거의 생기지 않는다.

## 영역 스펙 쓰는 법

- 위쪽(목적, 흐름, 기능)만 읽어도 이 영역이 무엇을 하는지 알 수 있게 쓴다. 고칠 때만 필요한 것은 "자세히"로 내린다.
- 흐름은 Mermaid `flowchart TD` 하나로 그린다. 주요 단계에만 ID를 붙이고, 로직은 차트 아래 두세 문장으로 덧붙인다.
- 기능은 완료된 것만 둔다. 기능 하나는 플레이어나 제작자가 한 번에 확인하는 것 하나이고, `### 기능 이름 (ID)` 제목 아래에 한 줄 요약과 세부 동작 2~4줄을 쓴다. 상태 태그는 쓰지 않는다.
- 영역당 기능은 15개 안팎을 넘기지 않는다. 같은 기능의 세부 규칙은 새 ID로 나누지 않고 그 기능의 세부 줄이나 "자세히 > 주의"에 더한다.
- 위쪽은 쉬운 말로 무엇을 하는지만 쓴다. 변수명, 메서드명, 수치 기본값은 쓰지 않는다. 화면에 나오는 문구는 따옴표 속에 그대로 적는다.
- 코드 이름은 "자세히 > 코드 단서" 표에만 둔다. 기능마다 진입점(클래스나 `클래스.메서드`) 한두 개만 적는다. 이름이 코드에 없으면 검사가 경고한다.
- 코드만 봐서는 알 수 없는 씬 오브젝트 구성과 연결은 "자세히 > 구성"에 쓴다.
- 기능은 의도가 아니라 지금 코드가 하는 일을 쓴다. 의도와 달라 보이면 메모에 적는다.
- 확인하지 못한 것은 "확인하지 못함"이라고 쓴다. 추측을 사실처럼 쓰지 않는다.
- 다른 영역의 규칙은 ID로 가리킨다(예: `BURDEN-04`).
- 필요 없어진 기능은 지운다. 지운 번호는 다시 쓰지 않는다.
- 변경 이력, 날짜, 작성자는 적지 않는다. 그런 기록은 작업 문서의 "결과"에 남는다.

## 스펙과 코드 잇기

- 코드에는 요구사항 ID나 스펙 번호를 쓰지 않는다. 문서를 고칠 때 코드까지 고치지 않기 위해서다. 검사가 막는다.
- 연결은 영역 스펙의 "코드 단서" 표, 작업 문서의 "어떻게 만드나", 커밋 제목의 ID(`git log --grep=BLINK-05`)로 한다.
- 코드 주석은 그 코드가 무엇을 하는지만 쓴다. "추가했다", "바꿨다" 같은 변경 이력은 쓰지 않는다.

## 작업을 마치면 보고할 것

작업 문서의 "결과"에 쓰고 사용자에게도 알린다: 바꾼 문서와 ID, ID별 고친 코드, 확인한 방법(컴파일, Play에서 따라 한 절차), 확인하지 못한 것.

## 커밋

- 작업은 ID를 괄호에 쉼표로 잇는다(예: `feat(BLINK-03,MEM-12): 요약`).
- 문서 없는 정리는 괄호 없이 쓴다(예: `chore: 사용하지 않는 에셋 정리`).

## 규칙 검사

사람이 직접 돌리지 않는다. 커밋할 때 훅이, `dev`·`master` 푸시와 PR에서 GitHub `spec-check`가 `Tools/check-specs.ps1`을 돌린다. 훅은 `git config core.hooksPath`가 `.githooks`여야 동작하며, 에이전트가 작업을 시작할 때 확인해 맞춘다.

- 오류(커밋이 막힘)
  - 영역 스펙: 번호 스펙 파일, README 표에 없는 스펙, 겹치는 접두어, 흐름 차트 없음, "기능" 절 없음, 진행 상태 절(진행 중, 진행 현황, 완료)이나 상태 태그가 있음, 접두어 불일치, 중복 ID, 다음 번호 이상인 ID, 옛 형식 요구사항 줄(`- **ID**`).
  - 작업 문서: 파일 이름 형식, 첫 줄 상태, 대상 줄, "무엇을 만드나" 절이 없음, 다음 번호 이상인 ID, 완료인데 영역 스펙 기능에 없는 ID, 같은 ID를 진행 중인 작업 둘이 맡음.
  - 그 밖: 코드 속 요구사항 ID나 스펙 번호, 커밋 제목 괄호 형식.
- 경고(커밋은 됨): 코드 단서 표가 없거나 기능 줄이 빠짐, 코드 단서 이름이 코드에 없음.
