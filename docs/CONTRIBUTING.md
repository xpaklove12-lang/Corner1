# 협업 안내

이 리포는 **스펙 문서 기반(SDD, Spec-Driven Development)** 으로 일한다. 게임이 어떻게 동작해야 하는지는 `docs/specs/`의 영역 스펙이 정하고, 코드는 스펙을 따른다. 스펙 목록과 접두어는 `docs/specs/README.md`, 바꾸려는 것에 맞는 스펙을 찾는 길잡이는 `docs/specs/ROUTER.md`, 양식은 `docs/specs/_TEMPLATE.md`, 코드 규칙은 루트 `AGENTS.md`에 있다.

## 1. 작업 순서 (SDD)

1. `docs/specs/ROUTER.md`에서 바꾸려는 것에 해당하는 영역 스펙을 찾아 끝까지 읽는다(특히 "다른 영역과의 접점"과 "알려진 문제").
2. 그 스펙에 요구사항을 `[작성중]`으로 더하거나 고친다. 새 요구사항은 그 스펙의 마지막 번호 다음을 쓴다.
3. `미결 사항`이 비어 있는지 확인하고, 사용자 승인을 받아 해당 요구사항을 `[승인]`으로 바꾼다.
4. 승인된 요구사항 ID 단위로 구현한다. 요구사항이 5개를 넘으면 구현 순서를 정해 묶음 단위로 승인받는다.
5. 구현 후 각 요구사항 ID가 어떤 코드로 충족되는지 보고하고, 스펙의 5절 코드 위치를 갱신하고, 상태를 `[구현완료]`로 바꾼다.

- 스펙에 없는 동작을 코드에만 넣지 않는다. 구현 중 스펙에 없는 요구가 발견되면 구현을 멈추고 스펙 수정을 제안한다.
- 스펙이 모호하면 추측하지 않고 질문한다.
- 커밋 제목 괄호에는 요구사항 ID를 쉼표로 잇는다(예: `feat(BLINK-03,MEM-12): 요약`). 스펙 없는 정리 작업은 괄호 없이 쓴다(예: `chore: 사용하지 않는 에셋 정리`).

### 스펙을 고칠까, 새로 만들까

- 동작을 바꾸거나 기능을 더하면 **그 기능을 이미 다루는 영역 스펙을 고친다. 같은 기능에 대해 새 스펙 파일을 만들지 않는다.**
- 새 스펙은 `ROUTER.md`에서 찾아도 맞는 영역이 없는 **새 기능 영역**일 때만 만든다. `_TEMPLATE.md`를 번호 없는 이름(소문자 영어, 낱말은 `-`로 잇는다, 예: `weather.md`)으로 복사하고, 겹치지 않는 대문자 접두어를 정해 `docs/specs/README.md`와 `ROUTER.md`에 등록한다.
- 기능이 사라지면 요구사항을 `~~MEM-07~~ (폐기: 이유)`로 남긴다. **요구사항 ID는 다른 의미로 다시 쓰지 않는다.**

## 2. 스펙 작성 규칙

- 스펙은 기능 영역마다 파일 하나이고, 파일 이름에 번호를 붙이지 않는다.
- 요구사항 ID는 `접두어-두자리번호`다(예: `BLINK-03`). 영역마다 번호가 따로 이어지므로 다른 영역을 맡은 사람과 번호가 겹치지 않는다.
- 같은 영역에 두 사람이 동시에 요구사항을 더해야 하면 먼저 시작한 사람이 번호를 쓰고, 다른 사람은 그 변경을 받은 뒤 다음 번호를 쓴다.
- 요구사항마다 상태 `[작성중]`, `[승인]`, `[구현완료]`, `[폐기]` 중 하나를 붙인다.
- `_TEMPLATE.md`의 절 구조와 순서를 그대로 따른다. 해당 없는 절은 지우지 않고 `해당 없음`으로 적는다.
- 모든 스펙에 동작 플로우차트를 넣는다(3절, Mermaid `flowchart TD`).
- 변경 이력, 날짜, 작성자, 버전은 적지 않는다. 스펙이 바뀌면 직접 덮어써서 항상 최신 상태 하나만 둔다.
- 스펙 목록 표(`docs/specs/README.md`)는 영역 파일을 새로 만들거나 이름을 바꿀 때만 고친다. 요구사항을 더할 때는 그 영역 스펙과 `ROUTER.md`의 ID 범위만 고친다.

## 3. 작업을 마치면 보고할 것

고친 스펙(파일과 요구사항 ID), 고친 코드(파일), 확인한 방법(컴파일 결과, 따라 한 검증 절차), 확인하지 못한 것.

## 4. 규칙 검사

`Tools/check-specs.ps1`이 다음을 검사한다: `docs/specs`의 번호 스펙 파일(`NNN-*.md`), `README.md` 1절 목록과 `ROUTER.md`에 없는 영역 스펙, 2절 요구사항 ID의 접두어 불일치와 중복, 커밋 제목 괄호의 옛 형식(`feat(015)`).

- **커밋 직전 검사**: 리포를 받은 뒤 처음 한 번 리포 폴더에서 `git config core.hooksPath .githooks`를 실행한다. 그 뒤로는 규칙을 어긴 커밋이 막히고 이유가 나온다.
- **GitHub 자동 검사**: `dev`·`master`에 푸시하거나 PR을 열면 GitHub Actions(`spec-check`)가 같은 검사를 돌린다. 실패하면 PR과 커밋에 빨간 표시가 뜬다.
- 직접 돌려 보려면 `powershell -ExecutionPolicy Bypass -File Tools/check-specs.ps1`을 실행한다.
