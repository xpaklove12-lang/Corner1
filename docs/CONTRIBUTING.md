# 협업 안내

게임이 어떻게 동작해야 하는지는 `docs/specs/`의 영역 스펙이 정하고, 코드는 스펙을 따른다. 기획, 이야기, 아트, 기술 자료가 어디 있는지는 [`README.md`](README.md)를 본다. 이 문서의 규칙은 스펙에만 적용한다. 스펙 목록은 [`specs/README.md`](specs/README.md), 양식은 [`specs/_TEMPLATE.md`](specs/_TEMPLATE.md), 코드 규칙은 루트 `AGENTS.md`에 있다. 이 문서의 절차는 에이전트가 따르고, 사람은 무엇을 만들지 말하고 승인만 한다.

## 진행 상황

따로 모은 파일이 없다. 각 스펙의 "진행 중" 절이 원본이다. `[제안]`은 승인 대기, `[개발중]`은 승인되어 작업 중이다. 진행 상황을 물으면 에이전트가 `dev`의 `docs/specs/*.md`에서 제목에 이 태그가 붙은 기능을 모아 답한다.

## 작업 순서

1. `specs/README.md`에서 바꾸려는 것의 영역 스펙을 찾아 읽는다. 고칠 요구사항 ID로 "자세히"의 주의도 찾아 읽는다.
2. 그 스펙의 "진행 중"에 요구사항을 `[제안]`으로 쓴다. 번호는 맨 위 "다음 번호"를 쓰고, 다음 번호를 1 올린다.
3. 이 스펙 변경만 짧은 브랜치로 `dev`에 먼저 합친다. 번호를 먼저 차지하고, 다른 사람에게 진행 중임을 알린다.
4. 사용자가 승인하면 `[개발중]`으로 바꾸고, 그다음 기능 브랜치를 따서 구현한다. 요구사항이 많으면 구현 순서를 정해 묶음으로 승인받는다.
5. 구현을 마치면 그 기능을 "완료"로 옮기고, 제목의 상태 태그와 "확인:", "범위 밖:" 줄을 지운다. "코드 단서" 표에 그 기능의 진입점을 적고, 고칠 때 깨뜨리기 쉬운 점은 "주의"에 남긴다.

- 스펙에 없는 동작을 코드에만 넣지 않는다. 구현 중 스펙에 없는 요구가 나오면 멈추고 스펙 수정을 제안한다.
- 스펙이 모호하면 추측하지 않고 묻는다.
- 같은 기능에 새 스펙 파일을 만들지 않는다. 새 스펙은 README에서 맞는 영역이 없을 때만 만든다. `_TEMPLATE.md`를 `영역-이름.md`(소문자 영어, 번호 없음)로 복사하고, 다른 영역과 겹치지 않는 대문자 접두어로 README 표에 등록한다.
- 스펙이 15편쯤 넘으면 `specs/gameplay/`, `specs/ui/`, `specs/tools/`, `specs/art/`처럼 분야별 하위 폴더로 나누고, README 표에 `gameplay/blink-maze.md`처럼 경로로 적는다.

## 여러 브랜치에서 일할 때

- 번호는 영역마다 따로 매기므로 다른 스펙끼리는 겹치지 않는다.
- 같은 스펙을 두 브랜치가 고치면 맨 위 "다음 번호" 줄에서 git 충돌이 나 겹침이 드러난다. 늦게 합치는 쪽이 자기 요구사항을 다음 번호로 바꾼다. 코드에는 ID가 없으므로 스펙만 고치면 된다.
- 위 3번처럼 스펙을 먼저 `dev`에 합치면 이런 충돌이 거의 생기지 않는다.

## 쓰는 법

- 위쪽(목적, 흐름, 진행 중, 완료)만 읽어도 무엇을 하는지 알 수 있게 쓴다. 고칠 때만 필요한 것은 "자세히"로 내린다.
- 흐름은 Mermaid `flowchart TD` 하나로 그린다. 주요 단계에만 ID를 붙이고, 로직은 차트 아래 두세 문장으로 덧붙인다.
- 요구사항 하나는 플레이어나 제작자가 한 번에 확인하는 기능 하나다. `### 기능 이름 (ID)` 제목 아래에 한 줄 요약과 세부 동작 2~4줄을 쓴다. 진행 중이면 제목 끝에 `[제안]`이나 `[개발중]`을 붙인다.
- 영역당 기능은 15개 안팎을 넘기지 않는다. 같은 기능의 세부 규칙은 새 ID로 나누지 않고 그 기능의 세부 줄이나 "자세히 > 주의"에 더한다.
- 위쪽(흐름, 진행 중, 완료)은 쉬운 말로 무엇을 하는지만 쓴다. 변수명, 메서드명, 수치 기본값은 쓰지 않는다. 화면에 나오는 문구는 따옴표 속에 그대로 적는다.
- 코드 이름은 "자세히 > 코드 단서" 표에만 둔다. 기능마다 진입점(클래스나 `클래스.메서드`) 한두 개만 적고, 변수까지 적지 않는다. 완료 기능의 이름이 코드에 없으면 검사가 경고한다.
- 코드만 봐서는 알 수 없는 씬 오브젝트 구성과 연결은 "자세히 > 구성"에 쓴다.
- 완료 요구사항은 의도가 아니라 지금 코드가 하는 일을 쓴다. 의도와 달라 보이면 메모에 적는다.
- 확인하지 못한 것은 "확인하지 못함"이라고 쓴다. 추측을 사실처럼 쓰지 않는다.
- 진행 중 요구사항에는 "확인:" 한 줄로 Play Mode에서 무엇을 보면 되는지 적는다. 이번에 하지 않을 것이 헷갈리면 "범위 밖:" 줄을 둔다. 테스트 코드는 쓰지 않는다.
- 다른 스펙의 규칙은 ID로 가리킨다(예: `BURDEN-04`).
- 필요 없어진 요구사항은 줄을 지운다. 지운 번호는 다시 쓰지 않는다.
- 변경 이력, 날짜, 작성자는 적지 않는다. 바뀐 내용은 덮어쓴다.

## 스펙과 코드 잇기

- 코드에는 요구사항 ID나 스펙 번호를 쓰지 않는다. 스펙을 고칠 때 코드까지 고치지 않기 위해서다. 검사가 막는다.
- 연결은 두 가지로 한다. 스펙의 "코드 단서" 표에서 진입점을 찾고, 커밋 제목의 ID(`git log --grep=BLINK-05`)로 그 기능을 바꾼 커밋과 파일을 찾는다.
- 코드 주석은 그 코드가 무엇을 하는지만 쓴다. "추가했다", "바꿨다" 같은 변경 이력은 쓰지 않는다.

## 작업을 마치면 보고할 것

고친 스펙과 요구사항 ID, ID별 고친 코드, 확인한 방법(컴파일, Play에서 따라 한 절차), 확인하지 못한 것.

## 커밋

- 스펙 작업은 요구사항 ID를 괄호에 쉼표로 잇는다(예: `feat(BLINK-03,MEM-12): 요약`).
- 스펙 없는 정리는 괄호 없이 쓴다(예: `chore: 사용하지 않는 에셋 정리`).

## 규칙 검사

사람이 직접 돌리지 않는다. 커밋할 때 훅이, `dev`·`master` 푸시와 PR에서 GitHub `spec-check`가 `Tools/check-specs.ps1`을 돌린다. 훅은 `git config core.hooksPath`가 `.githooks`여야 동작하며, 에이전트가 작업을 시작할 때 확인해 맞춘다.

- 오류(커밋이 막힘): 번호 스펙 파일, README 표에 없는 스펙, 겹치는 접두어, 흐름 차트 없음, 접두어 불일치, 중복 ID, 다음 번호 이상인 ID, 옛 형식 요구사항 줄(`- **ID**`), 진행 중 제목의 상태 태그 없음, 완료 제목에 남은 태그, 코드 속 요구사항 ID나 스펙 번호, 커밋 제목 괄호 형식.
- 경고(커밋은 됨): 코드 단서 표가 없거나 기능 줄이 빠짐, 완료 기능의 코드 단서 이름이 코드에 없음.
