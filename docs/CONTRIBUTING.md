# 협업 안내

게임이 어떻게 동작해야 하는지는 `docs/specs/`의 영역 스펙이 정하고, 코드는 스펙을 따른다. 스펙 목록은 [`specs/README.md`](specs/README.md), 양식은 [`specs/_TEMPLATE.md`](specs/_TEMPLATE.md), 코드 규칙은 루트 `AGENTS.md`에 있다. 이 문서의 절차는 에이전트가 따르고, 사람은 무엇을 만들지 말하고 승인만 한다.

## 진행 상황

따로 모은 파일이 없다. 각 스펙의 "진행 중" 절이 원본이다. `[제안]`은 승인 대기, `[개발중]`은 승인되어 작업 중이다. 진행 상황을 물으면 에이전트가 `dev`의 `docs/specs/*.md`에서 이 태그가 붙은 줄을 모아 답한다.

## 작업 순서

1. `specs/README.md`에서 바꾸려는 것의 영역 스펙을 찾아 읽는다. 고칠 요구사항 ID로 "자세히"의 주의도 찾아 읽는다.
2. 그 스펙의 "진행 중"에 요구사항을 `[제안]`으로 쓴다. 번호는 맨 위 "다음 번호"를 쓰고, 다음 번호를 1 올린다.
3. 이 스펙 변경만 짧은 브랜치로 `dev`에 먼저 합친다. 번호를 먼저 차지하고, 다른 사람에게 진행 중임을 알린다.
4. 사용자가 승인하면 `[개발중]`으로 바꾸고, 그다음 기능 브랜치를 따서 구현한다. 요구사항이 많으면 구현 순서를 정해 묶음으로 승인받는다.
5. 구현한 곳에 요구사항 ID 주석을 단다(아래 "코드 주석").
6. 구현을 마치면 그 줄을 "완료"로 옮기고, 상태 태그와 "확인:", "범위 밖:" 줄을 지운다. 고칠 때 깨뜨리기 쉬운 점은 "자세히"의 주의에 남긴다.

- 스펙에 없는 동작을 코드에만 넣지 않는다. 구현 중 스펙에 없는 요구가 나오면 멈추고 스펙 수정을 제안한다.
- 스펙이 모호하면 추측하지 않고 묻는다.
- 같은 기능에 새 스펙 파일을 만들지 않는다. 새 스펙은 README에서 맞는 영역이 없을 때만 만든다. `_TEMPLATE.md`를 `영역-이름.md`(소문자 영어, 번호 없음)로 복사하고, 다른 영역과 겹치지 않는 대문자 접두어로 README 표에 등록한다.

## 여러 브랜치에서 일할 때

- 번호는 영역마다 따로 매기므로 다른 스펙끼리는 겹치지 않는다.
- 같은 스펙을 두 브랜치가 고치면 맨 위 "다음 번호" 줄에서 git 충돌이 나 겹침이 드러난다. 늦게 합치는 쪽이 자기 요구사항을 다음 번호로 바꾸고, 그 ID를 쓴 코드 주석도 바꾼다.
- 위 3번처럼 스펙을 먼저 `dev`에 합치면 이런 충돌이 거의 생기지 않는다.

## 쓰는 법

- 위쪽(목적, 흐름, 진행 중, 완료)만 읽어도 무엇을 하는지 알 수 있게 쓴다. 고칠 때만 필요한 것은 "자세히"로 내린다.
- 흐름은 Mermaid `flowchart TD` 하나로 그린다. 주요 단계에만 ID를 붙이고, 로직은 차트 아래 두세 문장으로 덧붙인다.
- 요구사항 하나는 플레이어나 제작자가 한 번에 확인하는 기능 하나다. 한두 문장으로 쓰고, 영역당 15개 안팎을 넘기지 않는다. 같은 기능의 세부 규칙은 새 요구사항으로 나누지 않고 그 요구사항의 문장이나 "자세히 > 주의"에 ID를 앞에 붙여 더한다.
- 구현 방법은 쓰지 않는다. 클래스 구조, 수치 기본값, 화면 배치는 코드와 Inspector가 기준이다. 제작자가 조절하는 값은 필드 이름으로 가리킨다.
- 코드만 봐서는 알 수 없는 씬 오브젝트 구성과 연결은 "자세히 > 구성"에 쓴다.
- 완료 요구사항은 의도가 아니라 지금 코드가 하는 일을 쓴다. 의도와 달라 보이면 메모에 적는다.
- 확인하지 못한 것은 "확인하지 못함"이라고 쓴다. 추측을 사실처럼 쓰지 않는다.
- CSV 데이터만으로 충족되는 완료 요구사항은 줄 끝에 "(데이터)"를 붙인다.
- 진행 중 요구사항에는 "확인:" 한 줄로 Play Mode에서 무엇을 보면 되는지 적는다. 이번에 하지 않을 것이 헷갈리면 "범위 밖:" 줄을 둔다. 테스트 코드는 쓰지 않는다.
- 화면 문구는 `Data/Strings.csv` key나 따옴표 속 글 그대로 적는다. 다른 스펙의 규칙은 ID로 가리킨다(예: `BURDEN-04`).
- 필요 없어진 요구사항은 줄을 지우고, 그 ID를 쓴 코드 주석에서도 ID를 뗀다. 지운 번호는 다시 쓰지 않는다.
- 변경 이력, 날짜, 작성자는 적지 않는다. 바뀐 내용은 덮어쓴다.

## 코드 주석

- 요구사항을 판단하거나 시작하는 곳(진입 메서드, 판정 줄, 설정 필드)에 `// ID: 무엇을 하는지` 주석을 단다. 예: `// BLINK-05: 눈이 감긴 순간 판정 각도를 한 번에 확정한다.`
- 한 파일에 같은 ID는 한 번만 단다. 요구사항마다 코드 전체에 한두 곳이면 충분하다.
- "추가했다", "바꿨다" 같은 변경 이력은 주석에 쓰지 않는다.

## 작업을 마치면 보고할 것

고친 스펙과 요구사항 ID, ID별 고친 코드, 확인한 방법(컴파일, Play에서 따라 한 절차), 확인하지 못한 것.

## 커밋

- 스펙 작업은 요구사항 ID를 괄호에 쉼표로 잇는다(예: `feat(BLINK-03,MEM-12): 요약`).
- 스펙 없는 정리는 괄호 없이 쓴다(예: `chore: 사용하지 않는 에셋 정리`).

## 규칙 검사

사람이 직접 돌리지 않는다. 커밋할 때 훅이, `dev`·`master` 푸시와 PR에서 GitHub `spec-check`가 `Tools/check-specs.ps1`을 돌린다. 훅은 `git config core.hooksPath`가 `.githooks`여야 동작하며, 에이전트가 작업을 시작할 때 확인해 맞춘다.

- 오류(커밋이 막힘): 번호 스펙 파일, README 표에 없는 스펙, 겹치는 접두어, 흐름 차트 없음, 접두어 불일치, 중복 ID, 다음 번호 이상인 ID, 진행 중 줄의 상태 태그 없음, 완료 줄에 남은 태그, 커밋 제목 괄호 형식.
- 경고(커밋은 됨): 코드 주석에 없는 완료 ID, 스펙에 없는 코드 주석 ID.
