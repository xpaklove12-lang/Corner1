# 협업 안내

게임이 어떻게 동작해야 하는지는 `docs/specs/`의 영역 스펙이 정하고, 코드는 스펙을 따른다. 지금 개발 중인 것은 [`specs/STATUS.md`](specs/STATUS.md), 스펙 목록은 [`specs/README.md`](specs/README.md), 양식은 [`specs/_TEMPLATE.md`](specs/_TEMPLATE.md), 코드 규칙은 루트 `AGENTS.md`에 있다.

## 작업 순서

1. `specs/README.md`에서 바꾸려는 것의 영역 스펙을 찾아 읽는다.
2. 그 스펙의 "진행 중"에 요구사항을 `[제안]`으로 쓴다. 번호는 맨 위 "다음 번호"를 쓰고, 다음 번호를 1 올린다.
3. 사용자가 승인하면 `[개발중]`으로 바꾼다. `[개발중]`인 요구사항만 구현한다.
4. 구현을 마치면 그 줄을 "완료"로 옮기고, 상태 태그와 "확인:" 줄을 지운다.
5. `Tools/check-specs.ps1 -WriteStatus`로 `specs/STATUS.md`를 다시 만든다.

- 스펙에 없는 동작을 코드에만 넣지 않는다. 구현 중 스펙에 없는 요구가 나오면 멈추고 스펙 수정을 제안한다.
- 스펙이 모호하면 추측하지 않고 묻는다.
- 같은 기능에 새 스펙 파일을 만들지 않는다. 새 스펙은 README에서 맞는 영역이 없을 때만 만든다. `_TEMPLATE.md`를 `영역-이름.md`(소문자 영어, 번호 없음)로 복사하고, 새 대문자 접두어와 함께 README 목록에 등록한다.

## 쓰는 법

- 요구사항 하나는 확인할 수 있는 동작 하나를 한두 문장으로 쓴다("~하면 ~한다").
- 구현 방법은 쓰지 않는다. 클래스·메서드 이름, 수치 기본값, 화면 배치는 코드와 Inspector가 기준이다. 제작자가 조절하는 값은 이름만 가리켜도 된다.
- 화면 문구는 `Data/Strings.csv` key나 따옴표 속 글 그대로 적는다.
- 진행 중 요구사항에는 "확인:" 한 줄로 Play Mode에서 무엇을 보면 되는지 적는다. 테스트 코드는 쓰지 않는다.
- 다른 스펙의 규칙은 ID로 가리킨다(예: `BURDEN-04`).
- 필요 없어진 요구사항은 줄을 지운다. 지운 번호는 다시 쓰지 않는다. 다음 번호가 이를 막는다.
- 변경 이력, 날짜, 작성자는 적지 않는다. 바뀐 내용은 덮어쓴다.

## 커밋

- 스펙 작업은 요구사항 ID를 괄호에 쉼표로 잇는다(예: `feat(BLINK-03,MEM-12): 요약`).
- 스펙 없는 정리는 괄호 없이 쓴다(예: `chore: 사용하지 않는 에셋 정리`).
- 옛 번호(`feat(015)`)가 무엇인지는 [`specs/LEGACY-IDS.md`](specs/LEGACY-IDS.md)에서 찾는다.

## 규칙 검사

`Tools/check-specs.ps1`이 다음을 본다: 번호 스펙 파일, README 목록에 없는 스펙, 접두어 불일치, 중복 ID, 다음 번호 이상인 ID, 진행 중 줄의 상태 태그, 완료 줄에 남은 태그, 낡은 `STATUS.md`, 커밋 제목 괄호 형식.

- 커밋 직전 검사: 리포를 받은 뒤 한 번 `git config core.hooksPath .githooks`를 실행한다.
- GitHub 검사: `dev`·`master` 푸시와 PR에서 `spec-check`가 같은 검사를 돌린다.
- 직접 돌리기: `powershell -ExecutionPolicy Bypass -File Tools/check-specs.ps1`
